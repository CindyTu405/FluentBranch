git worktree：同一個 repo，同時開好幾個工作資料夾

以 .claude/worktrees/s-u1 為例，說明它是什麼、怎麼來的、在這個專案要注意什麼，以及怎麼安全刪掉。

1一句話解釋

worktree = 共用同一個 .git，但另外多開一個資料夾，在那裡 checkout 另一條分支。

平常一個 repo 只有一個工作資料夾，要換分支就得 git switch，手上的修改要先 commit 或 stash。有了 worktree，兩條分支可以各自待在自己的資料夾裡同時存在，互不打擾。

# 你剛才看到的
$ git worktree list
.../ai-chat-backend                         918a8cf [feat/landing-back]
.../ai-chat-backend/.claude/worktrees/s-u1  feed2bb [feat/s-u1-9]

第一行是「主 worktree」（就是 repo 本身），第二行是額外開的 worktree。

3它在這個專案是怎麼來的

位置是誰決定的

worktree 是 git 本身的功能，git 不限制它放在哪裡：git worktree add <路徑> 的路徑隨你指定，git 只在 .git/worktrees/<名字>/ 登記它。手動開的話，常見做法是放在 repo 旁邊（例如 ../ai-chat-backend-xxx），這樣就不會變成「repo 裡又包了一個 repo」。

.claude/worktrees/<名字>/ 這個位置符合 Claude Code 開 worktree 的慣例，所以 s-u1 很可能是某個 Claude Code session 開的。不過沒有任何紀錄能證明是誰建的，這一點是推測。

它經歷了什麼（從 git 歷史還原）

PLAN_v2.md 的 S-U1 規格寫著：在 feat/s-u1-user-ownership 開發，其他 session 共用此資料夾時改用 worktree。目的是讓兩邊的修改不會互相覆蓋同一批檔案。

4拆開來看：s-u1 裡面有什麼

那個 .git 檔案

$ cat .claude/worktrees/s-u1/.git
gitdir: .../ai-chat-backend/.git/worktrees/s-u1

主 repo 那邊也有對應的登記資料夾 .git/worktrees/s-u1/，裡面有它自己的 HEAD（指向 feat/s-u1-9）和 index。所以每個 worktree 有自己目前在哪條分支、自己的暫存區，但 commit 和分支都存在同一個地方。

5在這個專案要注意的坑

現象原因怎麼處理
git branch 裡 feat/s-u1-9 前面有 +，刪不掉 它正被 s-u1 這個 worktree checkout 中。git 不准刪一條「有人正在用」的分支，也不准同一條分支同時在兩個資料夾 checkout。 先 git worktree remove，再 git branch -d。
git status 一直出現 ?? .claude/worktrees/ 這個資料夾在 repo 裡面，但 .gitignore 沒有排除它。 把 .claude/worktrees/ 加進 .gitignore（另開一個小 commit）。
不小心 git add . git 會把 s-u1 當成「嵌在裡面的另一個 repo」，出現 embedded repository 警告，並把它加成一個奇怪的 gitlink。 同上，加進 .gitignore 就不會發生；已經加了就 git rm --cached .claude/worktrees/s-u1。
最重要的一點：資料庫只有一個。s-u1 的 .env 是 symlink，讀到的設定跟主資料夾一模一樣。backend/database.py 沒有 DATABASE_URL 環境變數時，會用 .env 的 POSTGRES_* 組出 localhost:5432，也就是 docker 的 chat_db。所以在 worktree 裡跑 alembic upgrade head，改的就是主資料夾正在用的同一個資料庫。S-U1-9 刪掉了 session_id 欄位，只要在 s-u1 套用那個 migration，main 那邊的資料庫也就跟著沒有這個欄位了。檔案可以隔離，資料庫不行。
docker 也一樣：docker-compose.yml 寫死了 container_name: chat_db、chat_api。在 worktree 裡再跑一次 docker compose up 會因為名字已被佔用而失敗。後端、資料庫請一律從主資料夾啟動；worktree 只拿來改檔案和跑不碰資料庫的檢查（例如 npm run build）。

6一個 worktree 的完整生命週期

git worktree add
（建資料夾＋分支）
→
在裡面改檔
commit
→
push、開 PR
merge
→
git worktree remove
（刪資料夾）
→
git branch -d
（刪分支）

s-u1 停在第四步之前。接下來你要做的就是最後兩格。

常用指令

# 看有哪些 worktree
git worktree list

# 新開一個（-b 同時建新分支，從 main 出發）
git worktree add -b feat/xxx ../ai-chat-xxx main

# 刪掉：會先檢查裡面有沒有未提交的修改，有就拒絕
git worktree remove .claude/worktrees/s-u1

# 如果資料夾被直接 rm -rf 掉了，用這個清掉 .git 裡殘留的登記
git worktree prune
不要直接 rm -rf worktree 資料夾。那樣 .git/worktrees/s-u1/ 的登記還在，git 會以為分支還被佔用，git branch -d 照樣失敗。用 git worktree remove，它會一次把資料夾和登記都清乾淨；真的已經 rm 掉了，就補一個 git worktree prune。

7現在就清掉 s-u1

# 1. 確認裡面沒有東西會遺失
git -C .claude/worktrees/s-u1 status --short   # 應該什麼都不印
git log --oneline main..feat/s-u1-9           # 應該什麼都不印

# 2. 刪 worktree（資料夾＋登記）
git worktree remove .claude/worktrees/s-u1

# 3. 分支前面的 + 消失了，現在可以刪
git branch -d feat/s-u1-9

# 4. 確認
git worktree list    # 只剩主資料夾一行

做完會釋放約 518 MB。若以後又用 Claude Code 開 worktree，merge 完記得一樣做這幾步。

8小練習

  1. 執行 cat .claude/worktrees/s-u1/.git，再 cat .git/worktrees/s-u1/HEAD，說明兩個檔案各指向哪裡。
  2. 執行 git branch，找出前面有 + 的分支，解釋為什麼現在刪不掉它。
  3. 不刪 worktree，直接試 git branch -d feat/s-u1-9，看 git 給的錯誤訊息。
  4. 照第 7 節清掉 s-u1，再跑一次 git branch，確認 + 消失、分支也刪掉了。
  5. 想一想：如果兩個 worktree 同時在不同分支跑 alembic upgrade head，各自的 migration 不一樣，資料庫會變成什麼狀態？
